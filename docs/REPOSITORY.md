## 产品边界

项目返回带来源的结构化网页证据，不负责生成最终答案，也不是自动规划研究步骤的 Agent。

- `search`：定位来源，返回候选 URL 和摘要。
- `fetch`：从已知 URL 或同一引擎会话的结果 ID 中提取段落。
- `gather`：搜索、提取、排序、控制预算，必要时只补充一轮搜索。
- 搜索适配器：Exa、Parallel、Tavily、Brave。
- 网页提取：Exa、Parallel、Tavily、Firecrawl；可选 Jina 重排、Cloudflare 充分性判断。
- 统一入口：SDK、CLI、Pi、stdio MCP、认证 HTTP MCP。

## 后续优先级

### 1. 在允许验证时确认可安装与真实行为

**干净安装与客户端入口。** 后续首先验证根目录干净安装、实际 tarball、CLI，以及目标客户端的插件发现、PATH 和权限。工作流定义正确或资产存在不证明 hosted CI、Windows、实际宿主已经通过。

**服务商契约。** 已有模拟 HTTP 契约和显式 opt-in 的 live 测试，但真实调用未在本轮验证。在用户允许、具备密钥并明确费用后，优先验证搜索、提取、限流、取消和实际字段格式。服务商默认优先级只是暂定值，应以真实查询的质量、耗时和成本决定是否调整。

**评估口径。** 合成回放可检查证据保留和预算，不代表真实排序质量。优先建立小规模人工标注集，包含中文、英文、相互矛盾的来源、时间过滤和提取失败；评价引用正确性与相关性，而不是只统计输出长度。`coverage` 仍应保持“停止提示而非真实性保证”的定位。

### 2. 有实际负载证据再做性能优化

**重复文本处理。** `fetchStage()` 用 `pageEvidence()` 判断页面是否可用，`fetch()` / `gatherEvidence()` 随后又进行清理、注入扫描、分段和排序。若 CPU 分析显示这里是热点，可让内部阶段复用一次处理结果，但不要因此持久存储用户网页内容。

**预算裁剪。** `budget.ts` 会多次完整序列化、计数和排序。当前输出与候选规模有上限，先保留简单实现；若自定义 tokenizer 或较大内容使耗时明显，再考虑单遍寻找最长段落、减少不必要的计数，仍须检查最终完整 JSON 的预算。

**并发重复请求。** 缓存保存的是已完成结果；共享一个引擎的相同并发查询在缓存填充前可能重复付费请求。只有确认存在实际重复后，再加入有界的 in-flight 去重，并明确单个调用者取消不能错误取消其他调用者的请求。

**HTTP 总体限额。** 当前默认最多 64 个会话、每会话 8 个活跃工具调用；这不是全服务 8 个调用的限制。如果部署为持续运行的共享单租户服务，应根据 API 配额增加全局调用/连接限额，并在边缘代理设置限流和 TLS。静态 bearer 认证不等于多租户隔离。

- 不把预发布版本、旧交付记录或模拟契约当作已发布、已实测的证明。
