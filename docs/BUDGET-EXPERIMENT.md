# 输出预算实验：16000 与更大预算（2026-11-01，真实读取）

目的：回答“把 `maxOutputChars` 从默认 16000 提高，能不能解决长文证据丢失”。这是测量，不是新契约；结论是**不能单独解决**。

## 方法

当前配置的默认 Reader（Jina，官方 HTTP MCP，无 focus）各读一次真实页面，把同一份**原始上游正文**分别按 16000 / 24000 / 32000 / 50000 走现有 `normalize()`。字符数为完整序列化 JSON 的 UTF-16 长度，不是 token。每个页面只抓一次，没有重读或改 binding。

## 保留率

| 页面 | 上游正文字符 | 16000 | 24000 | 32000 | 50000 |
|---|---:|---:|---:|---:|---:|
| RFC 9111 HTML | 60,176 | 24% (truncated) | 37% (truncated) | 50% (truncated) | 79% (truncated) |
| Node.js globals | 31,422 | 47% (truncated) | 71% (truncated) | 95% (truncated) | 100% |
| Node.js timers | 16,876 | 89% (truncated) | 100% | 100% | 100% |

预算与保留率基本线性：每 +8000 字符约多保留 8–24 个百分点，取决于文档冗余度。

## 预算解决不了的部分

- **RFC 9111 的 §5.2.2.5 no-store 正文在原始上游正文里就不存在。** 该 Reader 的普通读取对本页只返回前言、版权和目录，正文各节缺失；同一 URL 连读三次，字节完全相同（`sha256 b9e0df6a99b6…`），不是随机裁剪。加大预算把目录和引用往后推，仍然拿不到本节正文。
- 因此 16000 → 50000 能让“是否读到目标段落”从否变是的页面只有 globals 这类**上游完整、本地裁掉后半段**的页面。文档中已知的“改变预算不补回上游未返回内容”在这次测量里成立。
- 上游抓取时约 5% 的字符是 YAML 块标量的两格缩进和连续空行；压掉只省 4–6%，不足以改变结论，且会改动逐字证据，不做。

## 空白与成本

同一正文的 gzip 大小是 18,323 字节（RFC 页），说明压缩后成本远低于字符数暗示的量；但工具输出按未压缩字符计预算与上下文，不能拿压缩比替代实测。

## 结论与建议

- 需要长文完整覆盖率时，`maxOutputChars: 32000–50000` 有真实收益（globals 类页面 47%→95–100%，RFC 24%→50–79%）。这是纯配置，无代码改动。
- 不能靠预算解决“上游只返回前言”的页面；这类要靠 focus（能命中 §5.2.2.5）或换 Reader，与 `docs/RELEASE-2.1.0.md` 已写的边界一致。
- 本次不新增分页、快照或章节解析；无证据表明现有机制做不到，只表明预算不是唯一变量。

## 局限

单次抓取、两个站点、三页；Jina 的 chunk 选择在带 focus 时不稳定（同一 focus 两次抓取，一次含目标句、一次不含），因此不带 focus 的稳定页面才用于上表。字符数不是 token，未读模型侧账单。
